# 开发文档治理规范

本文档规定常态开发阶段如何维护设计文档、执行记录和开发状态，避免短期状态污染长期设计。

## 基本原则

GameKits 的文档分为三类：

1. 稳定维护文档：描述长期设计和长期实践，是代码实现的持续约束。
2. 决策记录：描述某个重要决策的背景、取舍和后果，通常追加不改写。
3. 开发执行记录：描述某次工作如何拆分、验证和关闭，是短期历史证据。

三类文档不能互相替代。稳定文档不能写临时状态；执行记录不能成为唯一设计来源；ADR 不能变成任务列表。

## 文档分类

| 类型     | 位置                              | 负责内容                                                      | 禁止内容                                    |
| -------- | --------------------------------- | ------------------------------------------------------------- | ------------------------------------------- |
| 项目设计 | `project-design.md`               | 项目定位、为什么做、长期目标、非目标、设计信条                | 当前状态、任务列表、阶段计划                |
| 架构设计 | `architecture.md`                 | 包边界、依赖方向、分层关系、跨模块约束                        | 单模块详细协议、阶段完成情况                |
| 模块设计 | `modules/<module>.md`             | 模块长期职责、公共协议、adapter/driver 边界、扩展点、长期实践 | 当前实现状态、临时 TODO、阶段计划、完成定义 |
| 应用设计 | `apps/<app>.md`                   | app/demo/editor 的长期体验、内容结构、交互方式和模块协作      | 阶段状态、任务拆分、临时验收记录            |
| 最佳实践 | `best-practices.md`               | 跨模块通用实践、性能经验、测试策略、反模式                    | 单次任务状态、不可变项目目标                |
| 发布手册 | `release.md`                      | 当前发布触发条件、Version PR、npm/GitHub Release 操作与排障   | 发布工具链取舍、历史执行记录、包长期边界    |
| 实现原则 | `implementation-principles.md`    | 代码质量、可测试性、可解释性、工程约束                        | 某次实现计划、历史决策过程                  |
| ADR      | `adr/`                            | 高影响决策的背景、候选方案、取舍和后果                        | 持续更新的开发状态、普通任务列表            |
| 执行记录 | `implementation/` 或任务系统 / PR | 某次工作流的拆分、review、测试证据、提交记录                  | 长期协议的唯一来源、模块最终设计            |

## 常态开发记录规则

常态开发不再维护一个全局线性状态文档。

不同工作按规模选择记录方式：

- 小修复：issue / PR / commit message 足够，不新增 implementation 文档。
- 单模块增强：若只改实现，记录在 PR；若改变模块设计，同步更新模块文档。
- 跨模块功能：可以新增 `docs/implementation/<topic>.md` 作为短期执行记录。
- 高影响决策：新增 ADR，再在长期文档中引用结论。
- 大型 app / demo / editor 工作：长期体验设计写 `docs/apps/`，执行状态写 implementation 记录或任务系统。

并行工作流可以同时存在，但每个工作流必须有清晰边界：

- 标题说明目标而不是“当前阶段”。
- 文档开头声明状态：`Active`、`Paused`、`Closed` 或 `Archived`。
- 只记录本工作流的任务、review、验证和提交。
- 不复制长期设计全文，只链接对应稳定文档。
- 关闭后不得继续追加新的无关工作。

## 关闭工作流

执行记录关闭时必须做收口：

1. 标记状态为 `Closed` 或 `Archived`。
2. 记录最后一次验证命令和结果。
3. 记录最终提交号或 PR。
4. 把可复用的稳定结论沉淀到长期文档。
5. 删除或迁移仍有价值的 TODO；不要把 TODO 留在已关闭记录中。
6. 确认长期文档没有引用已经过期的临时状态。

关闭后的 implementation 文档是历史记录，不再作为未来开发的事实来源。未来开发应阅读长期文档、ADR 和当前任务上下文。

## 稳定文档更新规则

稳定文档只写长期有效的事实：

- “模块应该如何被集成”
- “业务代码应该如何使用”
- “协议和边界是什么”
- “哪些依赖方向被禁止”
- “哪些实践已经被验证为长期推荐”

稳定文档不写：

- “当前做到哪”
- “下一步做什么”
- “本阶段暂不实现”
- “首轮先这样”
- “待实现”
- “某个 commit 的验收证据”

如果稳定文档需要提到实现成熟度，只能用长期语义描述能力边界，例如“该协议允许 adapter 提供可选 capability”，不要写“后续阶段补齐”。

## 状态信息放置规则

| 信息                   | 放置位置                                                 |
| ---------------------- | -------------------------------------------------------- |
| 当前 bug 是否修复      | issue / PR / commit                                      |
| 一个并行功能的任务拆分 | `docs/implementation/<topic>.md` 或任务系统              |
| 某模块的长期 API       | `docs/modules/<module>.md`                               |
| 某 app 的长期交互设计  | `docs/apps/<app>.md`                                     |
| 某技术取舍为什么成立   | `docs/adr/`                                              |
| 多模块依赖边界         | `docs/architecture.md`                                   |
| 跨模块最佳实践         | `docs/best-practices.md`                                 |
| 当前发布操作流程       | `docs/release.md`                                        |
| 常态开发文档怎么维护   | 本文档                                                   |
| 已关闭 MVP 的执行证据  | `docs/implementation/phase-15-abyss-delve.md` 和提交历史 |

## 冲突处理

当文档之间冲突时，按以下顺序处理：

1. 若是长期设计冲突，以 `project-design.md`、`architecture.md`、`modules/`、`apps/` 和 ADR 为准。
2. 若是执行记录与长期设计冲突，优先更新执行记录或补长期文档；不能让执行记录覆盖长期设计。
3. 若 ADR 与当前长期设计冲突，新增 ADR 或在原 ADR 顶部标记被 supersede；不要悄悄改写历史。
4. 若代码和长期文档冲突，必须判断是代码错误还是文档过期，并在同一工作流中修正。

## 命名建议

Implementation 文档命名应使用工作目标，而不是线性阶段编号：

- 推荐：`implementation/editor-data-pack-workflow.md`
- 推荐：`implementation/content-package-system-foundation.md`
- 推荐：`implementation/abyss-delve-combat-expansion.md`
- 不推荐：`implementation/next-stage.md`
- 不推荐：`implementation/current-status.md`
- 不推荐：`implementation/phase-16.md`

历史阶段文档可以保留原名，但必须标记为 `Closed` 或 `Archived`。

## MVP 之后

MVP 结束后不再维护单独的阶段路线或归档文档。已经关闭的大型阶段可以作为 implementation 历史记录保留；如果历史记录中的结论仍然有效，应迁移到稳定维护文档。

后续候选方向不放进单一“下一阶段”文档。它们应进入任务系统、路线规划工具、PR 或独立 implementation 工作流。任何候选方向一旦改变长期设计，必须同步更新 `project-design.md`、`architecture.md`、`modules/`、`apps/` 或 ADR。
